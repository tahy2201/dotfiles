# GitHub 操作の重要ルール（必読）

- **GitHub の issue／PR の作成・コメント投稿・編集は、必ず事前にユーザーの許可を取ってから実施すること。** 内容の下書きを提示し、承認を得るまでは実行しない（`gh` コマンドや API 経由も含む）。

# issue／PR 本文の書き方

issue や PR の説明文を書く（生成・更新する）ときは、以下に従うこと。

- **文体**: 「ですます調」にしない。「〜する」「〜した」などの常体（である調）で書く。
- **抽象度**: 「何を・なぜ」が伝わる粒度で書く。**どのファイルに何を追加したかの列挙は書かない**（差分を見れば分かる）。設定キー名・環境変数名・具体的なドメイン値・クラス名／メソッド名・props の配線経路などの実装詳細は原則書かない。設計上の判断（例: なぜ署名付き URL ではなく永続 URL なのか）は「なぜ」として簡潔に添える。
- **一貫性**: issue の完了条件・スコープと、実装・PR の内容を必ず一致させる。実装しない項目（スコープ外）は完了条件に残さず、スコープ外メモへ回すか削除する。issue と PR で用語・スコープを揃える。
- **構成の目安**: PR は「概要／変更内容／スコープ外（メモ）」、issue は「概要／スコープ／完了条件／依存」を基本とする。**これは目安であって埋めるべき型枠ではない**。書く中身がない節は見出しごと落とす。中身のない見出し＋予告だけを残さない。
- **変更内容の書き方**: 見出しで小分けにせず、フラットな箇条書きにする。1 項目は「何をしたか」を体言止めで短く書き、補足が要るものだけ子項目にぶら下げる。コンポーネントごとに `###` を切るのは、項目数が多く分類しないと読めない場合に限る。
- **動作確認**: 説明文には書かない（節も作らない）。確認した内容を残す必要があるときは PR のコメントに書く。説明文に「動作確認は別途コメントに記載する」のような予告も残さない。
- **役割分担**: issue には調査結果と方針のみを書く。修正内容は PR の説明文に、動作確認は PR のコメントに書く。同じ内容を issue と PR の両方に重複させない。
- **概要の範囲**: 概要には「いつ何が起きたか」「エラー内容」「原因の見立て」「暫定対応」までを書き、そこで止める。詳細な調査結果・恒久対応の検討はコメントに書く。調査によって結論がブレるため、何度も書き換わる内容を概要に置かない。「詳細はコメントに記す」のような予告も書かない。
- **時制**: issue を書く時点では実装は未完了なので、方針を述べる文体（「〜する」「〜が必要」）で書く。実装済みを示す書き方（「〜した」「確認済み」）は PR 側で使う。
- **簡潔さ**: 箇条書きを優先し、散文を並べない。表は複数の軸を比較するときだけ使い、2〜3 点を伝えるだけなら箇条書きで足りる。

# レビューコメントへの返信

- **文体**: **丁寧語（ですます調）**で書く。issue／PR の本文は常体だが、返信は相手に向けた発話なので使い分ける。
- **簡潔さ**: 要点のみに絞る（例:「ご指摘の通り漏れていましたので対応しました」「他に漏れがないか〇〇の方法で確認し、無いことを確認しました」）。
- **対応しない場合**: 理由を書く。判断の根拠（前提・制約・トレードオフ）まで添える。
- **コミットハッシュ**: 返信の**末尾に対応コミットのハッシュを付ける**。**ハッシュの前後には必ず半角スペースを空ける**（行末でも末尾に空白を置く）。

# コードコメントの書き方

- **重複させない**: 定義側（関数・ユーティリティ）のコメントで説明済みの経緯や背景を、呼び出し側で繰り返さない。1 箇所に集約する。

# 事実と根拠

- **確認していないことを「確認した」と書かない**: コードを読んだだけの推論は推論として書く。実測・実行・再現をしたときだけ「確認した」と書く。
- **エビデンスを残す**: 検証は使い捨てで済ませず、他の人が再現できる形（スクリプト・手順）で残す。PR に載せるならその成果物ごと提示する。
- **調査手法を検証する**: grep 等で「他に該当なし」と結論づけるときは、その検索式が取りこぼす書き方（別のメソッド・別の取得経路・分割代入など）がないか確認してから報告する。他者（レビューツール等）が使った手法をそのまま引き写さない。
- **主張は鵜呑みにしない**: 自分自身の推測にも、外部レビュー（Copilot 等の自動レビューコメント含む）の指摘にも、まず検証してから同意・反論する。「たぶんこう」を検証なしで通さない。
- **曖昧な語を使わない**: 「値域」「この層」「項目定数」のような、定義を示さない抽象語で説明しない。使うなら具体的な参照先（コード・データ・実例）を示す。

# レビュー対応の進め方

- **1 指摘 = 1 コミットで逐次進める**: 複数のレビューコメントを一括処理せず、「コメント確認 → 対応方針の提示 → 承認 → 修正 → 承認 → commit → 次のコメント」の順で 1 件ずつループする。
- **返信にはコミットハッシュを添えて対応関係を明示する**（上記「レビューコメントへの返信」のハッシュ書式ルールと合わせて運用）。

# 生成物の受け渡し

- 文章・文面・スニペットなどの成果物を生成するよう頼まれたときは、その成果物を必ずコードブロックで囲んで提示すること。地の文に混ぜて書かず、そのままコピーできる形にする。
- 成果物の中にコードブロック（```）が含まれる場合は、外側のフェンスを `~~~` にする。同じ記号で入れ子にすると途中でコピーが切れる。

# 作業用ファイルの出力先

調査メモ・設計検討メモ・SOW・分析結果などの作業用ファイルをリポジトリ内に出力するときは、以下に従うこと。

- **出力先は `.tahy/` 配下**とする。`docs/` には出力しない（`docs/` はコミット対象の正式なドキュメント置き場であり、作業用の一時ファイルを混ぜない）。
- `.tahy` はグローバル gitignore 済みのため、コミット対象にならない。作業用ファイルで `git status` を汚さないことが目的。
- リポジトリ直下からの相対で `.tahy/` を使う（例: `.tahy/<機能名>/spec-memo.md`）。必要に応じてサブディレクトリを作ってよい。
- **例外**: ユーザーが明示的に出力先を指定した場合、または成果物をコミットする意図が明確な場合（正式なドキュメント・README の更新など）は、その指示に従う。
