---
name: rv-all
description: レビュー依頼が来ている open な PR をすべて拾い、PR ごとにレビュー用セッションを立てる
---

自分にレビュー依頼が来ている PR を全部レビューする。PR ごとに別セッションを立て、終わったら一覧表にまとめる。

## 手順

1. **一覧を取る**
   ```bash
   gh search prs --review-requested=@me --state=open --json repository,number,title,author,url --limit 50
   ```
   0 件なら「レビュー依頼はありません」と伝えて終わる。

2. **既に立っている PR を除く**：`mcp__ccd_session_mgmt__list_sessions`（`limit: 50`）のタイトルに `<repo>#<番号>` を含むか、`cwd` が同じリポジトリで `prNumber` が一致するセッションがあれば、その PR はスキップする（作業のやり直し中のものを二重に立てない）。

3. **手元のフォルダを探す**：PR ごとに、`~/work` 以下で origin が `<owner>/<repo>` のリポジトリを探す。
   ```bash
   find ~/work -maxdepth 3 -type d -name '<repo>' -exec sh -c 'git -C "$1" remote get-url origin 2>/dev/null | grep -q "[:/]<owner>/<repo>\(\.git\)\?$" && echo "$1"' _ {} \;
   ```
   見つからない PR はスキップし、最後の報告で「手元にリポジトリがない」と伝える。

4. **タイトルを作る**：rv-detect フックと同じ形式にそろえる。
   ```bash
   echo '{"prompt":"<PR URL>"}' | python3 ~/.claude/hooks/rv-detect.py | jq -r .systemMessage
   ```
   出力の `[rv-detect] タイトル案: ` 以降をタイトルにする。取れなければ `[Rv] <repo>#<番号> <PRタイトル>`。

5. **セッションを立てる**（確認は挟まず、そのまま立てる。立てる前に対象の表だけ出す）：PR ごとに `mcp__ccd_session__start_session` を呼ぶ。同時に立てるのは **5 本まで**。残りは最後の報告で「次回 `/rv-all` で拾う」と伝える。
   - `initiation: "user_asked"`、`context: "fresh"`、`cwd`: 3 のフォルダ、`use_worktree: true`、`title`: 4 のタイトル、`wake_when_done: true`
   - `prompt` は種類で変える（`<PR URL>` を置き換え、それ以外はこのまま渡す）。
     - **dependabot / renovate の PR**：
       ```
       <PR URL>

       のreviewerにあたった。内容を確認してほしい
       - このライブラリは何をするものなのか
       - このプロジェクトにおいてどう使われているのか
       - 変更内容は何か
       - ライブラリの更新内容はどんなものか。プロジェクトに影響のある変更や、破壊的変更はないか
       - CI以外で動作確認するなら何をしたらよいのか

       最後に、判定（approve／要対応／要相談）と根拠を 3 行以内でまとめる。approve・close・push・コメントは承認を得てから行う。
       approve・close にはコメントを付ける。送る前に必ずコメントの下書きをコードブロックで見せ、文面への承認を得てから送る。本文なしで送らない（本文が空のレビューは後から本文を足せない）。
       ```
     - **それ以外の PR**：
       ```
       <PR URL>

       のreviewerにあたった。内容を確認してほしい

       * このPRは何を解決するものなのか（背景・関連 issue）
       * 変更内容は何か。変更前と後で挙動はどう変わるか
       * 変更箇所はプロジェクトの中でどこから使われているか。呼び出し元や下流（API・集計・他画面など）に影響はないか
       * バグ・考慮漏れ・既存の挙動を壊す変更はないか。issue の完了条件と実装は一致しているか
       * 既存のコメント（作者の動作確認・Copilot 等の指摘）は妥当か
       * CI以外で動作確認するなら何をしたらよいのか。作者の確認で足りていない観点はあるか
       * 総評（approve してよいか、指摘するならどの点か）

       最後に、判定（approve／要修正／要相談）と指摘の要点を 3 行以内でまとめる。GitHub への投稿は下書きを見せて承認を得てから行う。
       approve にもコメントを付ける。送る前に必ずコメントの下書きをコードブロックで見せ、文面への承認を得てから送る。本文なしで送らない（本文が空のレビューは後から本文を足せない）。
       ```
   - `background`：「`/rv-all` で、自分にレビュー依頼が来ている PR を PR ごとのセッションで並行レビューしている。このセッションの担当は上の 1 件だけ。マージはユーザーが行うので、マージも提案もしない。」

6. **まとめる**：全セッションが終わって起こされたら、各セッションの報告から一覧表を出す。

   | PR | 判定 | 要対応 | セッション |
   |---|---|---|---|

   セッション列は `[タイトル](#local_<id>)` のリンクにする。報告は鵜呑みにせず、判定が曖昧なものは「要確認」と書く。

## 注意

- このセッションからは GitHub に何も投稿しない。投稿・approve・close は各セッションで、コメントの下書きを見せてユーザーの承認を得てから行う。「approve して」とだけ言われても、下書きを見せずに送らない。
- `--review-requested=@me` はチーム宛ての依頼も含む。レビューを投稿すると一覧から外れるので、何度実行しても同じ PR は拾い直さない。
